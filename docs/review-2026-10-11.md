## Scope and plan

Review current implementation against `docs/00`–`05`, accepted refactor
plans and the public README/API contracts. This pass identifies discrepancies;
it does not change implementation or propose new product design.

1. Read the design baseline and later decisions; distinguish obsolete statements
   and deliberately deferred work from implementation defects.
2. Trace command workflows, manifest parsing, state comparison, backend calls,
   bootstrap, adoption, repository policy and CLI behavior.
3. Validate suspected discrepancies using focused, offline reproductions where
   the available R runtime permits; inspect relevant tests otherwise.
4. Record confirmed findings with impact, design references, implementation
   locations and validation limits. Keep design improvements for a later pass.

## 审阅结论

项目已经实现共享命令层、显式项目发现、初始化前分类、候选锁文件、
来源策略和结构化输出，基础方向与设计一致。但这些能力没有贯穿所有
工作流，存在以下 10 组偏差。P1 表示可能改变非预期状态或绕过关键契约；
P2 表示检查、输出、架构或验证覆盖与承诺不符。

本轮只记录事实、影响和证据，不修改实现，也不提出新产品设计。

## 优先级排序

按“非预期写入风险 → 核心契约影响 → 检查与输出可靠性 → 验证覆盖与架构”
排序。同一级内同时考虑触发范围和证据确定性。下表是处理顺序，正文编号
保持不变，方便追溯已有发现。P1 应优先处理；目前没有足够证据列为 P0。

| 顺序 | 级别 | 原发现 | 偏差 | 排序理由 |
| --- | --- | --- | --- | --- |
| 1 | P1 | 1 | adopt 同时传 apply/dry-run 会执行变更 | 直接违反只读要求，已确认调度到执行分支 |
| 2 | P1 | 3 | sync 部分路径绕过当前来源策略 | 项目收紧策略后仍可能恢复被禁止来源，影响契约执行 |
| 3 | P1 | 2 | sync 忽略普通版本约束及同版本来源变化 | 常规同步可报告成功却不满足 manifest，状态检查也可能漏报 |
| 4 | P1 | 5 | 初始化直接写正式锁文件，绕过统一校验 | 首次建立项目状态就缺少设计要求的保护流程 |
| 5 | P1 | 4 | adopt 实际副作用超出计划 | 预览不完整，且先 snapshot 后 restore 的风险需集成验证 |
| 6 | P2 | 7 | 仓库来源与可解析性检查结论矛盾 | 同一合法来源可能被误拒绝，影响严格模式和跨平台使用 |
| 7 | P2 | 6 | verify 严重程度及 R 版本比较错误 | 既有错误失败，也可能漏掉真实版本不兼容 |
| 8 | P2 | 8 | CLI dry-run 不打印计划，flag 校验不完整 | 用户无法审阅变更；json 与 dry-run 的使用边界不明确 |
| 9 | P2 | 9 | 跨平台 CI 指向错误项目且没有真实恢复 | 不能为承诺的跨平台恢复提供证据，降低后续修复的验证可信度 |
| 10 | P2 | 10 | adapter 之外仍直接调用 renv | 增加测试和维护耦合，当前直接用户影响低于上述行为问题 |

执行时，CI 验证缺口可随涉及跨平台的修复一并处理，不必机械等待到第九项。
普通版本约束执行属于已知未完成契约；本次排位体现其用户影响，不改变
这一历史分类。P1 的第五项中，未列入计划的调用已确认，真实锁文件损失
尚未复现，优先级没有建立在已发生数据丢失的假设上。

文档冲突单独排序：先明确 adopt 约束覆盖规则和仓库表/别名规则（会影响
修复验收），再统一默认仓库，最后修正 strategy/confirm 承诺和历史状态。
这些澄清可以与实现修复同步进行；明确的 dry-run 错误无需等待设计讨论。

## 实现偏差与未完成契约

### 1. P1：`adopt --apply --dry-run` 忽略只读要求

- 设计依据：`024-adopt-migration-plan.md` 的 Safety Rules 要求 dry-run
  不写文件、不安装、不 snapshot、不 restore。
- 实现位置：`R/cli.R:127`、`:153`。解析器记录 `dry_run`，但调度时仅用
  `!isTRUE(parsed$apply)` 决定是否执行，完全不读取 `parsed$dry_run`。
- 触发：同时传入 `--apply --dry-run`，任意顺序，都会传递 `dry_run = FALSE`。
  用户要求预览时可能实际改写 DESCRIPTION、配置、锁文件和库。
- 验证：离线 CLI 调度探针确认执行参数为 FALSE；后端已替换为桩，未实际写项目。

### 2. P1：`sync` 的比较模型没有覆盖版本和来源变化

- 设计依据：`01-product-principles.md` 要求 state 匹配 intent；
  `03-cli-design.md` 承诺按需 install/update；`022` 明确 DESCRIPTION
  中普通版本约束是有效 intent，同时把约束执行列为后续 sync/add 工作。
- 实现位置：`R/commands.R:372`、`:374`、`:440`；`R/utils.R:144`；
  `R/status-core.R:112`、`:928`。
- 普通依赖只比较包名。DESCRIPTION 要求 `pkg (>= 9.0.0)`、锁文件是
  `pkg 1.0.0` 时，sync 不安装或更新，直接 restore 旧版本。
  安装缺失包时传给 pak 的也是包名，没有传普通 DESCRIPTION 约束。
- override 仅比较 Version。同版本由仓库改成 GitHub，或更换仓库 URL，
  不会触发重新安装。`status/verify` 也主要比较包名和目录存在性，无法
  发现安装版本与锁定版本不符；库里仅有同名目录也会被视作已安装。
- 验证：对真实 cmd_sync 函数仅替换 manifest reader 和后端边界，确认
  `>= 9.0.0` 对 `1.0.0` 只调用 restore。其他分支经静态追踪确认。
- 分类：普通版本约束执行是设计中已经承认、但尚未完成的契约；
  不应当把它描述成 `022` 初始化分类重构引入的回归。

### 3. P1：`sync` 可以在未校验当前来源策略时恢复环境

- 设计依据：`02-architecture.md` 的变更生命周期要求先验证模型、
  执行后验证最终状态；README sync 流程要求 source preflight。
- 实现位置：`R/commands.R:424`、`:435`、`:447`；`R/utils.R:170`、`:316`。
- 来源检查仅在 `intent_install()` 或 `intent_snapshot()` 内发生。
  包名齐全、没有孤儿包时，两者都不运行，sync 直接 restore。
  因而项目把 GitHub 来源从允许改成禁止，或修改仓库策略后，旧锁文件
  仍可直接进入 restore 分支。
- 有孤儿包及待安装包时，先 remove/snapshot，再进入 install 的 preflight，
  与“验证模型后开始执行”的顺序也不一致。
- 各变更命令完成后均没有统一调用最终契约验证，却会报告 initialized、
  adopted 或 synchronized 成功。
- 验证：完整调用路径静态检查；未执行真实恢复或策略违规安装。

### 4. P1：迁移计划没有完整描述 apply 的副作用

- 设计依据：`024` 要求“write only the actions listed in the plan”以及
  apply 只执行已审阅的计划动作。
- 实现位置：`R/adopt-core.R:132`、`:389`、`:440`、`:449`；
  `R/utils.R:402`。
- 计划动作只包含仓库、bootstrap 依赖和 `.Renviron`；apply 额外设置
  renv snapshot type、hydrate intent、snapshot 和 clean restore。
  `install_self` 也没有进入计划构造，所以 hydrate 与 never 的计划
  无法反映其后端副作用差异。
- `intent_sync_project()` 实际是 snapshot 当前库再 restore，未使用
  cmd_sync 的缺失包安装流程，也没有最终 verify。迁移一个带锁文件、
  但本地库尚未恢复的项目时，可能先失败，或以不完整本地库生成状态，
  而不是根据已有 intent/lock 恢复；具体 renv 结果尚未集成验证。
- 验证：计划构造与 apply 路径静态对照。确认未列出的调用存在；
  不声称已经复现真实锁文件丢包。

### 5. P1：新项目初始化绕过候选锁文件与统一校验

- 设计依据：`02-architecture.md` Lockfile Normalization 和
  `04-renv-boundary.md` Lockfile Write Rule 要求后端先写候选状态，
  经 intent 规范化、验证后才替换正式锁文件。
- 实现位置：`R/backend.R:1`、`:19`、`:22`、`:29`；`R/commands.R:111`。
- `backend_init()` 直接把 renv snapshot 写入正式 `renv.lock`，随后
  仅覆盖仓库表；没有调用统一来源验证或候选锁文件流程。
  `install_self = "never"` 时也不会再通过 hydration 触发普通 snapshot。
- 初始化 snapshot 明确只包含 pak/renv。对于已有合规 DESCRIPTION、
  但无 renv 状态的项目，没有安装其中普通依赖的步骤。
- 已有状态分支走的是 snapshot/restore 辅助函数，也未保证 snapshot type
  持久设置为 explicit。README 对所有初始化路径的保证比实现更强。
- 验证：静态调用路径确认；未运行真实 renv 初始化。

### 6. P2：`verify` 对信息级提示判失败，且 R 版本比较忽略 patch

- 设计依据：`027` 区分 warning/error；R 版本检查函数自身将 session
  与 lockfile 的差异标为 informational，DESCRIPTION 的版本约束是契约。
- 实现位置：`R/commands.R:500`；`R/status-core.R:451`、`:519`、`:534`。
- `ok = nrow(issues) == 0`，任何 info/warning 都使 CLI verify 以错误退出。
  即使当前 R 与 lockfile R 都满足 DESCRIPTION，仅版本不同也会失败。
- 约束解析和比较只使用 major/minor；`4.5.2` 会被认为满足 `>= 4.5.9`。
- `intent_check_platform_repos()` 在 policy mode=off 时直接返回空，
  而 `027` 明确要求 off 时仍报告 warning。
- 验证：三个场景均通过离线核心/命令边界探针确认。

### 7. P2：仓库来源检查与可解析性检查对同一锁文件结论矛盾

- 设计依据：`020`、`027` 和 README 支持 URL 别名匹配，兼容旧式
  `Repository: https://...`。
- 实现位置：`R/status-core.R:238`、`:696`、`:784`。
- 旧式 Repository URL：source policy 接受声明过的 URL，但 repo
  resolvability 不直接比较 Repository URL，因此 verify 又报告不可解析。
- 包记录使用别名、其 URL 仅存在于 `$R$Repositories` 时：resolvability
  能按 URL 接受；source policy 不读取该表，只看包记录 URL，反而拒绝。
  严格 snapshot 可因此拒绝本应通过的同源别名记录。
- 验证：两种最小锁文件均运行实际核心函数，确认相反结论。

### 8. P2：CLI 普通 dry-run 没有打印操作计划

- 设计依据：`03-cli-design.md` 要求 dry-run report planned actions，
  `004` 已实现可读的 `print.intent_plan()`。
- 实现位置：`R/cli.R:1`、`:46`、`:62`、`:76`；`exec/intent:2`。
- add/remove 返回计划但没有 print；sync 只在 `--json --dry-run` 时输出
  计划。真实入口通过 invisible 返回，Rscript 不会自动打印返回对象。
  结果 add/remove dry-run 没有计划输出；sync 通常只显示进度消息。
- 验证：用桩替换 cmd 层、模拟入口 invisible 返回，三条命令 stdout
  计划输出均为空。
- 相关输入校验缺口：`sync --json` 未要求 dry-run，仍执行变更；
  add/remove 接受 `--json` 却不提供 JSON 计划。这与 CLI 文档的 flag
  适用范围不一致。此部分经静态检查确认。

### 9. P2：跨平台 CI 没有验证承诺的真实恢复场景

- 设计依据：`027` Result 声称已经加入 Linux create → Windows/macOS
  restore pipeline；该文档另有将真实 pipeline 留待单独工作的描述，
  二者本身需要统一。
- 实现位置：`.github/workflows/cross-platform-restore.yaml:37`、`:46`、
  `:63`、`:99`。
- Linux 在临时目录 init 后，`intent::add('dplyr')` 未传 project，也未
  setwd；按真实 resolve_project 算法，它会针对 checkout 中的 DESCRIPTION
  操作，而不是待上传锁文件的临时目录。因此 artifact 没有经过预期的 add。
- 消费端只有 macOS，没有 Windows，也没有 sync/restore，只运行 verify
  并过滤缺库问题。它证明的是部分元数据可检查，不是真实跨平台可恢复。
- 验证：工作流与 resolve_project 静态对照；未触发远程 CI。

### 10. P2：后端隔离没有满足已完成重构的边界规则

- 设计依据：`04-renv-boundary.md` rule 3；`013` 的目标是 backend.R
  之外不再直接调用 renv。
- 实现位置：`R/utils.R:299`、`:310`；`R/adopt-core.R:440`。
- intent_snapshot 直接调用 renv lockfile read/write；adoption core 直接
  调用 renv settings。更换后端或隔离测试仍须理解 renv 细节。
- 验证：全 R 目录检索 `renv::`，确认以上执行调用在 adapter 之外。
  注释、文档字符串中的 renv 提及不计入。

## 文档自身的不一致（不直接判定为实现错误）

1. **默认仓库。** README、CLI 设计和 `021` 示例仍写默认 PPM/RSPM；
   代码 `load_default_repos()` 与 init roxygen/Rd 已改成 CRAN。
   `027` 又按 CRAN 为当前默认描述。实际默认可确定，当前决策基线不统一。
   空 `INTENT_DEFAULT_REPOS` 的“强制显式声明”承诺也没有对应初始化停止
   检查：helper 返回空仓库后 cmd_init 会继续；未经真实安装验证。
2. **adopt 是否保留 bootstrap 约束。** `024` 的 clarified decisions 与
   result 明确使用 override=TRUE，代码和测试符合；同文档 apply/safety/test
   部分仍要求用户约束优先。不能简单把当前覆盖行为判成实现偏离：需先
   标记旧条款被哪项决策取代。
3. **仓库表是否必须完全相等。** `02/04` 要求 `$R$Repositories` 与声明
   完全一致；后续 `020` 与 README 允许增加同 URL 别名。代码补别名本身
   符合后续方案，但上层架构规范没有同步。`020` 也仍标 planned。
4. **adopt 的 strategy/confirm 承诺。** `adopt_build_candidates()` 的
   strategy/confirm 参数未使用，两种 strategy 的候选发现行为相同；
   confirm 没有选择或确认流程。`024` 已把交互候选选择列为 follow-up，
   因此应归为已知延期；公开 roxygen 却仍承诺 prompt，文档需要区分。
   `024` Result 后的 README/CLI follow-up 也有部分已经完成、未更新状态。
5. **历史问题写成当前问题。** `00/02/04` 的 Current Pain/Smell/Risks
   仍说没有命令层、公共函数依赖 renv::project，实际上已由 `001/003/013`
   解决。它们应被看作历史背景，不能再次报成代码缺陷。

- 审阅对象：本地工作树的 R 实现、公开文档与 Rd、核心设计、后续重构
  决策、相关 testthat 测试及 CI；没有查询在线信息或执行远程操作。

## 后续实施记录（2026-10-11）

以上是最初审阅时的历史证据。后续按 028/029 计划实现了 CLI 预览保护、
共享依赖协调流程、版本与来源校验、候选锁保护、初始化/迁移约束保留，
并将 renv 调用收敛到后端适配层。原先断言缺陷的探针已由回归测试入口替代；
当前验证范围见 029 与后端能力矩阵，不能再使用最初“未运行 testthat”的
说明描述实施后的状态。

后端实验也发现了新的明确边界：当前解析器不会自动遍历历史版本满足上界；
精确历史版本可以解析。缓存包携带构建镜像名称的问题已有基于实际解析计划的
来源证据适配。跨平台恢复需以远端 CI 结果为准。
